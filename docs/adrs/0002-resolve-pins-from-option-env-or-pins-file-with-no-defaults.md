# 0002. Resolve pins from an option, the image environment or a pins file, with no bundled defaults

## Status

Accepted. Partly superseded by
[0003](0003-pin-apt-installed-clis-by-upstream-version-with-a-verified-repo-key.md):
apt-installed CLIs pin a version only, and 0003 states exactly when a
channel counts as set.

## Context

Every CLI feature in this collection installs a tool at an exact version
and checks each download against a sha256. The question is where the
version and sha come from, and what happens when nobody supplies them.

- **What `install.sh` can see.** Feature options arrive as upper-cased
  environment variables (`sha256_amd64` becomes `SHA256_AMD64`). Only the
  feature's own folder is copied into the build, so `install.sh` sees
  neither the consumer's workspace nor the host's environment. Features
  are built as layers on top of the consumer's image or Dockerfile, so
  `ENV` values and files baked into that image are visible. A host
  variable can reach an option through `${localEnv:VAR}` in
  `devcontainer.json`
  ([json reference](https://containers.dev/implementors/json_reference/)).
  That leaves three input channels: an option, an image environment
  variable, and a file in the image.
- **Bundled defaults would go stale and hide the choice.** A default pin
  in the feature would mean shipping a new feature version for every
  upstream release, and a consumer who never set a pin would silently get
  whatever version the feature author picked. The user decided against
  bundled defaults.
- **Checksums are per arch.** Per-arch artifacts need one sha each
  (`sha256_amd64`, `sha256_arm64`); an artifact that is the same on every
  arch (the Keycloak tarball) needs one `sha256` (user decision).
- **Variables must be unambiguous across features.** Several features can
  read from the same image environment and pins file, so each needs its
  own prefix.
- **Shell.** `install.sh` runs inside the consumer's base image. The
  official collection mostly uses bash (`aws-cli`, `github-cli`,
  `docker-in-docker`); `common-utils` starts in POSIX `sh` only so it can
  install bash on Alpine. This collection supports Debian and Ubuntu only,
  and both ship bash as an essential package, including the bare
  `debian:13` and `ubuntu:24.04` images.
- **Testing without defaults.** `devcontainer features test` has two
  kinds of tests. The autogenerated test installs a feature with its
  default options on the `--base-image`; scenarios in
  `test/<id>/scenarios.json` bring their own options and image. With no
  default pins, the autogenerated test can only fail.
- **Renovate and JSON.** Base already bumps pinned versions through
  Renovate `customManagers` regexes keyed on `# renovate:` comments. JSON
  has no comments, and the Dev Container CLI passes every key of a
  feature's options object into the build as an environment variable, so
  an annotation inside the options would leak into the install.

## Decision

**Resolution order.** We will resolve each CLI feature's version and
sha256 from the first of these channels that sets either of them:

1. the feature options: `version` and `sha256_amd64` / `sha256_arm64`, or
   `sha256` for an arch-independent artifact;
2. the image environment: `<ID>_VERSION` and `<ID>_SHA256_AMD64` /
   `<ID>_SHA256_ARM64`, or `<ID>_SHA256`;
3. the pins file, at the `pins_file` option's path (default
   `/etc/devcontainer-features/pins.env`), holding the same `<ID>_*` keys
   as `KEY=value` lines.

If no channel sets either value, the install fails with an error that
names all three channels. There are no bundled defaults.

**Every pin option is declared with `"default": ""`.** That covers
`version`, the sha options and `pins_file` (empty means the default
path). The Dev Container CLI writes every declared option, defaults
included, to `devcontainer-features.env` and sources it with `set -a`
before `install.sh` runs. An empty `VERSION` therefore always replaces a
`VERSION` inherited from the base image's `ENV` or exported by an earlier
feature, which would otherwise be taken as the option. For the same
reason, `install.sh` reads `/etc/os-release` only in a subshell.
`ssl-ca`'s `certs`, `urls` and `sha256s` follow the same rule, since it
resolves them the same way.

The rule is enforced by a prek hook, `scripts/check-feature-options.sh`.
In every feature whose `install.sh` sources `install-lib.sh`, each of
`version`, `sha256`, `sha256_amd64`, `sha256_arm64`, `pins_file`,
`certs`, `urls` and `sha256s` that it declares must have
`"default": ""`. A feature that declares `version` must also declare
`pins_file`.

**Version and sha come from the same channel.** "The first non-empty value
wins" is applied to the pair, not to each variable on its own. A channel
that sets a version without the sha for this arch, or a sha without its
version, is an error; it is never completed from a later channel. Taken
per variable, an image's `ENV <ID>_SHA256_AMD64` could pair silently with
a `version` option set by someone else, and the check would then fail, or
worse, pass for an artifact neither party meant.

**The check always runs:** `echo "<sha>  <file>" | sha256sum -c -`. A
mismatch deletes the download and fails the install.

**Downloads retry, with a bounded connect time.** `il_fetch_verified`
runs `curl -fsSL --connect-timeout 10 --retry 3 --retry-max-time 60
--retry-connrefused`. curl itself retries timeouts, `ECONNREFUSED` and
HTTP 408/429/5xx. It doesn't retry other connect errors such as
`EHOSTUNREACH` or `ENETUNREACH`, so the library retries DNS and connect
failures (curl exit 6/7), resets and truncated transfers (18/52/55/56) up
to 4 calls, as base's `scripts/develop.sh` does. That makes at most 16
attempts, each with a connection phase (DNS, TCP and TLS) of at most 10s,
so failing to connect costs at most about 200s with the backoff sleeps.
A transfer that stalls after connecting is not bounded. There is no
`--max-time`, because artifact sizes vary and a hard total cap would
need its own decision.

**Naming rule, no exceptions.** `<ID>` is the feature id upper-cased with
`-` turned into `_` (`cli-keycloak` gives `CLI_KEYCLOAK`). Every variable a
feature reads is `<ID>_<OPTION>`, with the option id upper-cased the same
way.

**The pins file is parsed, never sourced.** Only `KEY=value` lines are
read, optionally after leading blanks and `export` plus blanks (spaces or
tabs). Blank lines and `#` comment lines are skipped, and blanks after `=`
are trimmed. A value that starts with a quote runs to the matching quote
and the rest of the line is ignored. An unquoted value ends before a
trailing ` # comment`, with trailing blanks dropped. Nothing is expanded.
Only the feature's own `<ID>_*` keys are looked up, so one file can hold
the pins of every feature. A repeated key takes its last value.
Versions must match `[A-Za-z0-9][A-Za-z0-9._+~-]*` and shas must be 64 hex
digits, because both end up in URLs and file names.

**bash.** `install-lib.sh` and every `install.sh` are bash
(`#!/usr/bin/env bash`), and shellcheck checks them as bash.

**One library, copied.** `common/install-lib.sh` implements this as
`il_resolve_pin <ID> <true|false>`, which sets `IL_VERSION` and
`IL_SHA256`. Each feature carries a byte-identical copy as
`src/<id>/install-lib.sh` (a prek hook fails on drift) and sources it:

```bash
#!/usr/bin/env bash
set -euo pipefail
# shellcheck source=install-lib.sh
. "$(dirname "$0")/install-lib.sh"
```

**Tests run scenarios only, on every base image.** `features.yml` runs
`devcontainer features test --skip-autogenerated` for each feature. Before
the run it rewrites the feature's `scenarios.json` for the matrix base
image: a scenario with `"image"` gets the matrix image, and a scenario
with `"build"` gets it as the `BASE_IMAGE` build arg, so its Dockerfile
starts with `ARG BASE_IMAGE` and `FROM ${BASE_IMAGE}`. `scenarios.json`
must therefore be strict JSON (no comments), which `jq` can rewrite.

**Renovate annotations in `scenarios.json`.** A scenario that pins a
version carries a `"//renovate"` key whose value is
`datasource=<datasource> depName=<depName>`, optionally followed by
` extractVersion=<regex>`. The key sits at the scenario's top level, never
inside a feature's options, and comes before the `"version"` it tracks,
with no closing `}` between them. In practice it is the scenario's first
key, and a scenario pins at most one versioned feature this way. The
regex reads the raw JSON text, so `extractVersion` must not contain a
backslash or a quote (`^v(?<version>.*)$` needs neither):

```json
{
  "option_channel": {
    "//renovate": "datasource=github-releases depName=peak/s5cmd extractVersion=^v(?<version>.*)$",
    "image": "mcr.microsoft.com/devcontainers/base:trixie",
    "features": {
      "cli-s5cmd": {
        "version": "2.3.0",
        "sha256_amd64": "<64 hex>",
        "sha256_arm64": "<64 hex>"
      }
    }
  }
}
```

The image-environment and pins-file channels' test fixtures, a
`test/**/Dockerfile` or a `test/**/*.env` file, use base's comment form
on the line directly above the version:

```dockerfile
# renovate: datasource=github-releases depName=peak/s5cmd extractVersion=^v(?<version>.*)$
ENV CLI_S5CMD_VERSION=2.3.0
```

**Renovate bumps the version, never the sha.** It can't compute the
checksum of an artifact it doesn't download. A Renovate PR for a test pin
therefore fails the feature tests (sha mismatch) until a maintainer puts
the new shas next to the new version. That failure is the intended
signal. `.github/renovate.json` gives `test/**` updates their own group,
never automerged, with a PR note saying so.

## Consequences

- A consumer always states what they install. Forgetting a pin fails the
  build with a message that names all three places to set it, rather than
  installing an unreviewed default.
- Upstream releases need no feature release; a consumer bumps their own
  pin. The flip side is that every consumer maintains pins, which is why
  the image environment and a repo-wide pins file exist as channels.
- A pin is always set as a version and sha together, in one place. A team
  that sets pins in its base image can still override both with options,
  but never just one of them.
- The autogenerated `devcontainer features test` is unused; every test is
  a scenario, and coverage depends on writing scenarios for each channel.
  An expected failure (wrong sha, missing version) can't be a scenario,
  since a failed install fails the run; it has to be checked from inside a
  scenario's test script.
- Renovate's test-pin PRs always need a human to update the shas. The
  failing test makes that hard to miss, and it is the honest outcome: a
  green test would mean the sha was never checked.
- `ssl-ca` resolves its own `certs`, `urls` and `sha256s` the same way
  (option, then `SSL_CA_*` in the image environment, then the pins file)
  but doesn't use `il_resolve_pin`, because it takes lists rather than a
  version.
